# 赛博寺庙祈愿选寺入场需求

- 需求标识为 `001-wish-temple-recommendation`，尚未创建对应开发分支。
- 整理日期为 2026-11-11，状态为需求草案。
- 本版按用户确认仅调整选寺入场，采用“统一场景、多寺院配置”。
- 面向希望在线祈愿、寻找情绪寄托或了解佛寺文化的普通用户。

## 目标与已确定范围

用户先选择祈愿类型，再从系统推荐的五座适配佛寺中选择一座。用户可以换一批，浏览其他适配寺院。推荐介绍需要突出每座寺院的地方、建筑、故事和祈愿特色。

所有启用寺院共用现有3D场景。所在地、特色介绍与祈愿适配理由集中在入场前呈现。用户选寺入场时，山门匾额显示该寺名称，随后沿用原有场景流程与交互。

本次功能终点为成功进入统一场景。祈愿完成流程、留念反馈、场景内提示文案、房间与多人机制均沿用已有逻辑，不纳入本次改造。祈愿类型仅用于入场前推荐，场景只接收展示寺名所需的最小信息。

入口提供简短说明“以统一虚拟场景呈现各地佛寺文化”。现实寺院的历史、建筑介绍与本产品的场景描述分别编写，避免把现实特色写成已经存在于虚拟场景中的设施。

已确定覆盖大陆31个省级地区及港澳台，共34个地区。每区选择2至5座知名或有代表性特色的佛教寺院。现有目录含84座、212条祈愿适配关系。

八个入口名称已经确认。前端展示、寺院卡片及筛选文案均采用以下两字名称。

| 名称 | 标识 | 覆盖诉求举例 |
| --- | --- | --- |
| 求财 | wealth | 收入、生意、回款、债务压力 |
| 事业 | career | 求职、晋升、项目、创业 |
| 姻缘 | love | 遇见合适的人、感情和睦、婚姻长久 |
| 健康 | health | 自己及亲友安康、康复祝愿 |
| 学业 | study | 升学、考研考公、资格考试、学习专注 |
| 家庭 | family | 家庭和睦、父母与孩子、求子添丁 |
| 转运 | fortune | 事情有转机、重新开始、迎新纳福 |
| 心安 | peace | 放下烦恼、整理心事、找回勇气 |

“健康”的名称已确定。原目录“健康平安”中出行平安的归属，按下方假设处理。

## 用户流程

1. 选择祈愿类型。入口显示“你想求什么？”和八个类别。
2. 获得5座推荐寺院。先按类型匹配，再随机抽取。
3. 查看介绍或换一批。介绍、推荐理由与来源均在入场前查看。
4. 选择寺院。确认入场时选定的寺院身份。
5. 进入统一场景。匾额显示所选寺名，本次新增流程结束。

现有入场流程要求的身份、房间等参数，仍按原要求收集并透传。具体与选寺页如何衔接，在实现前检查现有入口后确定，不另行定义房间或身份规则。

## 功能需求

以下规则中的假设在文末列明，供产品确认后用于实现。

- **FR-001 分类入口**。系统 MUST 展示且仅展示已确认的八个入口，每次按一种类型进行推荐。分类标识与显示名称分开维护。
- **FR-002 寺院目录**。系统 MUST 按34个地区维护寺院，每区2至5座。每座允许关联多个类型，并分别记录主推／次推、适配理由、依据类别与来源。关闭、删除或未配置该类型的条目必须从候选池排除。
- **FR-003 五寺推荐**。系统 MUST 先筛选类型，再从符合条件的寺院中随机无放回抽取五座。同一批寺院ID必须唯一。候选不足五座时展示实际数量并提示，候选为空时显示“暂时还没有适配的寺院”。
- **FR-004 换批与记录**。系统 MUST 在换批时优先使用该类型在当前会话尚未展示的寺院。未见数量不足五座时，先取完未见条目，再从已见条目补足，并提示部分寺院已展示过。补足时优先避开上一批。看完该类全部寺院后，允许提示并开启下一轮。
- **FR-005 卡片与详情**。每张卡片 MUST 展示寺名、地区、特色标题、简短原创介绍、适配类型、当前类型的推荐理由，以及查看详情／进入寺院操作。卡片应说明适配依据，详情提供来源。切换类型时，推荐理由必须随所选类型变化。
- **FR-006 依据与文案**。系统 MUST 区分民间口碑、信仰文化关联、策划延展。只有来源明确记载的内容可以标记为民间口碑。文案必须保持真实建筑、故事与地域特色，MUST NOT 把策划标签显示为公认专长、灵验概率或效果保证。
- **FR-007 请求与显示状态**。系统 MUST 区分加载、空结果、失败和成功。换批期间避免重复请求，失败时保留上一批并提供重试。已成功生成的同一批次在重试时返回同一结果，避免无故跳过未见寺院。
- **FR-008 入场展示与衔接**。所有启用寺院 MUST 使用同一现有场景入口。入场时仅将寺院ID及匾额显示名等必要展示信息交给场景。匾额必须对应最终选定的寺院，长寺名可使用配置短名并保持可读。身份、房间等已有入场参数与流程必须正常衔接。共用场景加载失败时允许重试，并保留选寺结果。
- **FR-009 改造边界**。系统 MUST 将分类、推荐、详情与换批状态封装在入场模块内。场景内部仅增加寺名展示的最小适配。进入后的原有操作与行为必须保持现有规则，不引入按寺院或祈愿类型分支的后续业务流程，也不修改多人房间划分。

## 内容配置

每座寺院至少包含以下信息。

| 信息 | 用途 |
| --- | --- |
| 唯一标识、寺名、别名 | 识别、去重，区分同名寺院 |
| 省级地区、城市／区县 | 展示所在地，支持地域配置 |
| 佛教类别、历史佛寺说明 | 说明汉传、藏传及历史背景 |
| 一句特色标题、现实寺院介绍 | 让用户快速产生兴趣，区分历史文化事实与虚拟空间 |
| 匾额显示名 | 入场时展示寺名，兼顾长寺名与别名 |
| 祈愿类型及主推／次推 | 决定可以进入哪个候选池 |
| 每种类型的推荐理由及依据来源 | 解释为什么推荐给当前用户 |
| 寺院启用状态 | 控制能否参与入场推荐 |

共用场景入口由产品统一配置，每座寺院无需单独配置模型或后续交互逻辑。

## 入场与场景的衔接

| 位置 | 展示内容 | 数据使用边界 |
| --- | --- | --- |
| 分类入口 | 八类祈愿 | 用于匹配推荐候选 |
| 推荐列表与入场前详情 | 寺名、所在地、特色介绍与适配理由 | 由入场模块负责 |
| 场景山门匾额 | 所选寺院名称或配置短名 | 只消费寺名展示信息 |
| 场景内部 | 原有界面及交互 | 沿用现有逻辑 |

例如，用户选择“求财”，在入场前查看灵顺寺的杭州北高峰与财神民俗介绍。选中后进入现有场景，匾额显示“灵顺寺”。选择“姻缘”并进入红螺寺时，同一场景匾额显示“红螺寺”。两次入场后的操作流程一致。

同名寺院通过唯一ID及入场前所在地信息区分。长寺名的完整名称始终保留在入场前详情，匾额可以使用已配置短名。

卡片文案示例沿用现有原创目录。

- 灵顺寺的标题可用“登上北高峰，愿辛苦有收获”，以北高峰和五显财神民俗说明求财关联。
- 红螺寺的标题可用“红螺山下，给相遇留个位置”，以古松、竹林与已有姻缘口碑形成记忆点。
- 国清寺的标题可用“隋塔与溪桥之间，让心安住”，以溪桥、隋塔和院落表现静心体验。

## 本版假设

- **A-001**。首版只选一级类别，不新增心愿输入、细分愿望选择或登录门槛。现有入口已经要求的信息按原流程处理。
- **A-002**。当前草案默认匹配池内等概率随机。之前目录中的5／3／1加权及同地区限额属于策划建议，尚未获得用户明确确认。
- **A-003**。切换类型后恢复该类型上一批结果和已见记录，点击“换一批”才继续抽取。会话至少跨页面往返保留，关闭浏览器后是否继续保留待定。
- **A-004**。“健康”此次仅改显示名称，暂保留原有亲友安康、康复与出行平安主题。求子仍归家庭。
- **A-005**。初版允许文化关联和策划延展条目进入推荐池，并向用户标明依据。若改为仅允许民间口碑，部分类型不足五座，需补充调研或接受较少结果。
- **A-006**。保留历史佛寺及主祀佛菩萨、附祀民间神祇的佛寺。现实宗教活动与开放状态另行核定。
- **A-007**。若用户通过现有返回方式回到入场页，保留当前类别与推荐批次，允许重新选寺。首版不新增场景内换寺入口。
- **A-008**。匾额属于当前用户入场时的展示信息，不用于改变当前多人房间的分配规则，也不覆盖其他用户所选寺院的展示。实现时需要确认现有场景的匾额渲染方式。

## 待确定事项与现状

1. 推荐是否使用均匀随机，还是口碑优先的加权随机，以及是否限制同批地区数量。
2. 文化关联与策划延展能否进入正式推荐池。这会影响每类可推荐数量。
3. 推荐进度保留多久，是否需要跨设备同步。
4. 现有身份、房间选择与场景初始化如何接到新入场页，以及匾额文字的最小配置接口。实现前查看现有代码后确定。

运行目录 `mirror/entry/catalog.json` 已迁移84座寺院、两字分类、启用状态、匾额显示名及逐类型依据。此前交付的Excel和JSON研究附件保留早期四字名称，运行程序以entry目录为准。已有介绍与推荐理由用于入场前页面。目录没有逐寺细分愿望标签，不能由“家庭”标签推定所有相关寺院均适合求子。
